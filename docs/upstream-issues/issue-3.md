`_get_identification_file_ids_batch` (`app/library.py`, ~line 320) selects candidates
with `OR(identified == False, identification_type == 'filename' [keys loaded],
orphaned)`. Three classes of files get re-identified on **every** cycle, forever:

1. **Failed files** (`identified = False`): `identification_attempts` and
   `last_attempt` are written (~line 484) but never read as a filter anywhere — a
   corrupt or keyless file is re-opened and re-decrypted every 2 hours in perpetuity.
2. **Orphan trap**: when `identify_appId()` returns `(None, None)` (app ID unknown to
   the cnmts index), the content is filtered out but the file is still marked
   `identified = True` (~line 470) with **zero `app_files` rows** — so it matches the
   `orphaned` predicate forever and is fully re-identified every cycle despite being
   "identified".
3. With keys loaded, every `identification_type == 'filename'` file retries each cycle
   (fine when it upgrades to cnmt, a permanent loop when it keeps failing).

At scale this is brutal: 2,000 such files × ~0.5s of scattered network reads ≈ 17
minutes of pure random I/O per 2-hour cycle producing zero state change.

**Suggested fix:** actually use the existing columns — exponential backoff on
`identification_attempts`/`last_attempt` (e.g. 2h base doubling to a 7-day cap, reset
on successful CNMT identification), and don't mark zero-content files as identified so
the same backoff governs them.
