## Issue 1 — SQLite runs without WAL or busy_timeout: "database is locked" aborts scans under concurrency

**Title:** [Bug] "database is locked" aborts library scans and freezes the web UI (SQLite runs without WAL/busy_timeout)

**Body:**

With a large library (20k+ files) and normal traffic, scheduled scans die with:

```
ERROR (app) Error during scheduled library scan job: (sqlite3.OperationalError) database is locked
```

and the batch of files being ingested is rolled back — so the next 2-hourly scan
re-ingests the same files (`Getting file info (n/250): ...` repeats forever), and while
the lock is contended all waitress threads queue up and the web UI freezes.

**Root cause** (all in current `master`):

- The only connect-time pragma is `PRAGMA foreign_keys=ON` (`init_db`, `app/db.py`
  ~line 699). The database therefore runs in the default DELETE journal mode: any
  reader blocks a writer's commit and vice versa, and pysqlite's default 5s timeout
  turns contention into `OperationalError`.
- No `SQLALCHEMY_ENGINE_OPTIONS` are set, so the pool is 5+10 connections serving
  32 waitress threads (`AEROFOIL_WSGI_THREADS`) plus 4 scheduler workers, the watchdog
  thread, the debounce runner and download threads — `QueuePool limit` timeouts under
  load on top of the lock errors.
- Interestingly `app/titles.py` already opens its own index DBs with `timeout=30` and
  `synchronous=NORMAL` — the main DB just never got the same treatment.

**Suggested fix** (small, contained):

```python
# connect hook
cursor.execute("PRAGMA journal_mode=WAL;")
cursor.execute("PRAGMA synchronous=NORMAL;")
cursor.execute("PRAGMA busy_timeout=30000;")

# app config
app.config["SQLALCHEMY_ENGINE_OPTIONS"] = {
    "connect_args": {"timeout": 30}, "pool_size": 20, "max_overflow": 30,
}
```

WAL lets readers proceed during writes and writers queue instead of erroring. Running
this on a 20k-file library eliminated the lock errors entirely.

**Working fix on our fork:** https://github.com/freefrank/AeroFoil/commit/4959234d1371db7fd5223e72e31df11406fde6ad — happy to open a PR.
(Reviewer note: WAL adds `-wal`/`-shm` sidecar files next to the DB.)

## Issue 2 — Write transactions span slow file I/O during scan/identification, holding the DB lock for minutes

**Title:** [Bug] Same files re-ingested every scan cycle after a lock error (write transaction held while reading/decrypting files)

**Body:**

Two related spots keep a SQLite write transaction open across slow filesystem work,
which is what makes issue #<SQLite/WAL issue number> actually fire in practice:

1. `identify_library_files` (`app/library.py`): the loop commits every
   `_IDENTIFY_COMMIT_INTERVAL = 50` files, and inside that window each file goes
   through `titles_lib.identify_file(filepath)` — a container open + AES-XTS header
   decryption that takes 50ms–2s per file on network mounts. The transaction starts at
   the first autoflush, so the write lock is held across up to 50 files' worth of disk
   and crypto work — routinely minutes. Every other writer times out meanwhile.
2. `add_files_to_library` (`app/library.py`): `get_file_info` runs inside the
   transaction, committed only every 100 files. When the commit finally collides with
   another writer, the whole scan job aborts and the uncommitted batch is lost —
   observable as the same "Getting file info (n/250)" lines re-appearing every cycle.

**Suggested fix:** two-phase batches — do the file I/O first with nothing pending in
the session, then apply all results in one short write transaction; retry a contended
commit once and skip just that chunk instead of aborting the whole scan. Implemented
and tested on a 20k-file library (initial ingest also got ~5x faster: 16s → 3.2s
because the lock is never held across I/O).

**Working fix on our fork:** https://github.com/freefrank/AeroFoil/commit/abd7821f0b8c893ffa21e64746771687c272309a — can open a PR.

## Issue 3 — Identification retries the same failing files forever; "orphaned" files are re-identified every cycle

**Title:** [Bug] Failing or orphaned files are fully re-identified on every scan cycle forever (no retry backoff)

**Body:**

`_get_identification_file_ids_batch` (`app/library.py`, ~line 320) selects candidates
with `OR(identified == False, identification_type == 'filename' [keys loaded],
orphaned)`. Three classes of files get re-identified on **every** cycle, forever:

1. **Failed files** (`identified = False`): `identification_attempts` and
   `last_attempt` are written (~line 484) but never read as a filter anywhere — a
   corrupt or keyless file is re-opened and re-decrypted every 2 hours in perpetuity.
2. **Orphan trap**: when `identify_appId()` returns `(None, None)` (app ID unknown to
   the cnmts index), the content is filtered out but the file is still marked
   `identified = True` (~line 470) with **zero `app_files` rows** — so it matches the
   `orphaned` predicate forever and is fully re-identified every cycle despite being
   "identified".
3. With keys loaded, every `identification_type == 'filename'` file retries each cycle
   (fine when it upgrades to cnmt, a permanent loop when it keeps failing).

At scale this is brutal: 2,000 such files × ~0.5s of scattered network reads ≈ 17
minutes of pure random I/O per 2-hour cycle producing zero state change.

**Suggested fix:** actually use the existing columns — exponential backoff on
`identification_attempts`/`last_attempt` (e.g. 2h base doubling to a 7-day cap, reset
on successful CNMT identification), and don't mark zero-content files as identified so
the same backoff governs them.

**Working fix on our fork:** https://github.com/freefrank/AeroFoil/commit/8a196655ca98bd6ae7015608b3b8c30c50cb58da — can open a PR.

## Issue 4 — Scan/rebuild locks guard flags, not work: multiple full scans can write the DB concurrently

**Title:** [Bug] Scheduled scan, download jobs and rebuilds can all write the database at the same time (locks only guard status flags)

**Body:**

The locks around scanning/rebuilding only protect flag assignment, so several
combinations of full jobs can write SQLite concurrently (compounding the
`database is locked` failures):

- The download jobs call `scan_library` directly with no guard:
  `run_downloads_job(scan_cb=scan_library, ...)` every 5 min and
  `check_completed_downloads(scan_cb=scan_library, ...)` every 30s (`app/app.py`
  ~lines 287/290), plus two request handlers (~lines 5205/5212). None of these check
  `scan_in_progress`, so they interleave with the scheduled 2-hourly scan.
- `scan_library_api` has a TOCTOU: it checks `scan_in_progress` inside `scan_lock` but
  sets it **outside** the lock (~line 7914) — two concurrent POSTs both pass.
- `_run_post_library_change` (~line 7839) takes `library_rebuild_lock` only to flip
  `library_rebuild_status['in_progress']` and releases it before doing the rebuild —
  two rebuilds can run concurrently (e.g. the debounced runner vs the direct call in
  the delete-content API).
- The maintenance job checks only the conversion flag, not the scan flag, and both it
  and `update_db_and_scan` register with `run_first=True` — guaranteed concurrent at
  startup.

**Suggested fix:** one guarded scan entry point (check-and-set under the lock, used by
the scheduler, the API and the download callbacks), a non-blocking run lock held for
the whole rebuild (a second request schedules a trailing debounced run instead of
duplicating the sweep), and a scan-flag check in maintenance.

**Working fix on our fork:** https://github.com/freefrank/AeroFoil/commit/d9dbf28d21e5a6dfaea242fe558b6271ade20bc7 — can open a PR.

## Issue 5 — File watcher: unguarded getsize can kill the observer thread; per-event stability scan is O(events x tracked)

**Title:** [Bug] File watching silently stops during mass copies/moves (unhandled FileNotFoundError kills the watchdog thread; per-event stability scan is O(n²))

**Body:**

Two problems in `app/file_watcher.py`:

1. **Silent watcher death:** `_track_file` calls `os.path.getsize(file_path)` with no
   exception handling (~line 94). A file that disappears between event emission and
   dispatch (near-certain during a mass move) raises `FileNotFoundError` inside
   watchdog's dispatch loop and kills the emitter thread — file watching silently
   stops for the rest of the process lifetime, with no log line.
Same failure family as #131 (a background thread dying silently and processing stopping) — this one is the watchdog observer thread instead of the debounce runner.

2. **O(E²) stat storm:** `collect_event` ends with an unconditional synchronous
   `self._check_file_stability()` (~line 152), which walks the entire `tracked_files`
   dict doing 2 stats per entry. Copying/moving 10k files into a library ≈ 10⁸ stat
   syscalls on the observer thread (hours on NFS/SMB), and it defeats the
   `@debounce(5)` path (`debounced_check_final`) that already exists two lines above
   for exactly this purpose. Meanwhile the kernel inotify queue overflows and events
   are silently dropped.

Also worth noting: `tracked_files` is mutated from both the observer thread and the
debounce runner with no lock.

**Suggested fix:** try/except around the getsize calls (missing file → untrack),
delete the synchronous per-event stability call (trusting the existing debounce), and
a small lock around `tracked_files`.

**Working fix on our fork:** https://github.com/freefrank/AeroFoil/commit/0fcbe44be4182a82d217969fa0f72e3c020ccb63 — can open a PR.
